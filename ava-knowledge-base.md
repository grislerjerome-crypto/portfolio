### Specialty: GoHighLevel CRM
Pipelines, routing and follow through. I start with the states, records and rules. Then I build the workflows around them. Supporting tools shown: GoHighLevel, Google Sheets, Zapier, Make, n8n. Studies: Ticket system, Lead routing, Recovery. These are concept designs, not deployed client outcomes.

#### Ticket system: A support desk built around the ticket
One pipeline for the work. Clear routes for new requests, repeat submissions and a customer who goes quiet.
Problem: A contact can have several issues over time. Storing the latest issue on the contact loses context and creates duplicate work.
Plan: I map the states first, then define the opportunity fields, owner rules and the workflow attached to each stage.
Decisions: The opportunity owns the ticket details. The contact remains the customer record. Check for an open ticket before creating a new opportunity. A priority flag alerts the team without inventing another pipeline stage.
Testing before handoff: Submit the same request twice. Only one open ticket should remain. Reply while awaiting information. The ticket must return to its owner. Change status before a timer expires. The stale reminder must not send.
Handoff: Pipeline map, field dictionary, message templates, workflow build sheet and an exception checklist.
Reference note: the ticket lifecycle is adapted from Brewed Ops as design inspiration, not a client claim. Its timing and reopening rules are illustrative configuration, not platform defaults.

#### Lead routing: The build plan behind a booked call
I separate lead capture from appointment confirmation so the customer receives the right message once.
Problem: A form, calendar and follow up sequence can all act on the same contact and send conflicting messages.
Plan: Define the source fields and consent rules, create the pipeline, then build qualification, assignment and appointment workflows separately.
Decisions: Capture source and consent at entry. Appointment booked is its own event, not an assumption after form submission. Reply, booking and opt out are explicit stop conditions.
Testing before handoff: A form submission alone must not send an appointment confirmation. A booked contact must leave the nurture path. A repeat webhook must not create a duplicate opportunity.
Handoff: Trigger map, field and tag guide, booking workflow and a short ownership SOP.

#### Recovery: A recovery path with a clear exit
Missed calls and missed appointments get a useful next step, without turning into endless follow up.
Problem: Recovery workflows often keep messaging after a customer has already replied or rescheduled.
Plan: Choose the exact missed event, check permissions, then define recovery, rescheduling and owner review as distinct outcomes.
Decisions: Use event specific entry rules rather than broad contact changes. Check the current state again after every wait. An unresolved case goes to a person, not another unbounded message loop.
Testing before handoff: Reschedule during the wait. Recovery messages must stop. Respect opt out and local sending hours. No response should create an owner task at the agreed cutoff.
Handoff: Recovery workflow, message set, stop conditions and escalation rules.

### Specialty: Hermes Agent
Agent teams, tools and recurring work. I define the goal and the boundaries. Agents handle focused work; evidence and human judgment guide the handoff. Supporting tools shown: Hermes Agent, n8n, Slack. Studies: Agent framework, Scheduled work, Memory and skills. These are concept designs, not deployed client outcomes.

#### Agent framework: How I build with an agent team
I own the brief and the decisions. An orchestrator coordinates focused agents for research, implementation and review.
Problem: One long AI conversation mixes research, assumptions and implementation, making weak decisions harder to catch.
Plan: Agree on acceptance criteria, assign bounded specialist tasks, collect evidence and review the result before anything is published.
Decisions: Each specialist gets a focused brief and separate conversation context. Separate context is not a security sandbox. File access and permissions still need explicit boundaries. A reviewer checks actual output. The orchestrator does not treat a confident summary as proof.
Testing before handoff: Check sources against the claims in the brief. Exercise the built page or workflow, including failure cases. Require approval before publishing or connecting production accounts.
Handoff: Working preview, verified checks, source notes and a documented handoff.

#### Scheduled work: Recurring work with a defined handoff
The schedule is only the trigger. The real design is the task context, allowed actions, evidence and delivery.
Problem: A recurring AI task is not useful if its scope is vague, failures are invisible or nobody receives the result.
Plan: Specify the routine, timezone, required integrations and report format. Add delivery and a failure path before scheduling it.
Decisions: Morning brief: 0 8 * * * in the configured timezone. Weekly research: 0 9 * * 1 with source linked findings. The host and scheduler must be running. An offline computer cannot execute the routine.
Testing before handoff: Verify the timezone and next intended execution. Test missing data, a failed integration and an empty report. Confirm the report reaches the intended destination without exposing secrets.
Handoff: Schedule specification, task instructions, delivery format and failure checklist.

#### Memory and skills: A repeatable way to build, not a repeated prompt
Memory keeps durable context. Skills keep the procedure. Tools produce the artifact and checks prove it works.
Problem: Repeating the same setup wastes time, but treating old context as unquestionable truth causes a different problem.
Plan: Separate stable preferences from task instructions, load the relevant procedure, then verify against the current project.
Decisions: Store durable preferences in memory, not every temporary detail. Keep reusable build and QA procedures in skills. Update a procedure when evidence shows it is wrong; do not treat it as perfect recall.
Testing before handoff: Confirm the procedure matches the current tools and repository. Check the real artifact rather than claiming a successful build from file creation alone. Keep private context out of public handoffs.
Handoff: Reusable procedure, current project notes, a tested artifact and clear limitations.

### Specialty: Shopify Operations
Orders, stock and exception handling. I map the normal order path and the things that interrupt it, then give every exception an owner. Supporting tools shown: Shopify, Google Sheets, Slack, Zapier. Studies: Order system, Stock control, Return workflow. These are concept designs, not deployed client outcomes.

#### Order system: An order desk designed around exceptions
Paid orders move toward fulfillment. Address, stock and payment issues branch into owned exception queues.
Problem: The normal orders are easy. The failures get buried across inboxes, spreadsheets and shipping portals.
Plan: Map the order states, source of truth and ownership first. Define which checks can run automatically and which need a person.
Decisions: Shopify remains the order record. Trackers support it rather than becoming a conflicting copy. A hold needs a reason, owner and next action. Only confirm fulfillment when the required operational event has occurred.
Testing before handoff: A repeated event must not create a second exception task. A held order must not enter the ready to pack queue. Tracking updates must belong to the correct order and shipment.
Handoff: Order state map, exception tracker, owner rules and daily operations SOP.

#### Stock control: Inventory signals that lead to a decision
Available stock, committed orders and supplier lead time belong in the same conversation.
Problem: A low stock alert without context creates noise. An oversold item without an owner creates a customer problem.
Plan: Define sellable stock and the reorder rule, connect commitments, then build an approval and exception path.
Decisions: Distinguish on hand, committed and available stock. Use supplier lead time and demand context when recommending replenishment. Purchases and customer refunds stay behind the store’s approval rules.
Testing before handoff: Review multi location stock before declaring an item unavailable. Deduplicate repeated threshold alerts. Verify the customer promise against a confirmed supplier date.
Handoff: Inventory check routine, reorder review sheet and shortage response SOP.

#### Return workflow: Returns with policy and ownership built in
A request, return receipt and refund decision are different events. I keep them connected without skipping the checks.
Problem: A loose email thread can promise a refund before eligibility, receipt or authority has been established.
Plan: Start from the store’s policy, map the evidence needed at each step, and keep the final financial decision with an authorized person.
Decisions: Match every request to the original order and item. Record return condition before deciding whether stock can be restored. Separate exchange fulfillment from refund authorization.
Testing before handoff: Test a request outside the return window. Check a partial return and an item that cannot be restocked. Confirm no refund is implied before approval.
Handoff: Return decision map, customer templates, inspection checklist and approval log.

### Specialty: Digital Marketing
Strategy, measurement and useful tests. I connect the business objective to the offer, customer journey and measurement before choosing tactics. Supporting tools shown: Meta, Google Analytics, Canva, Instagram, LinkedIn, GoHighLevel. Studies: Campaign plan, Measurement, Experiment plan. These are concept designs, not deployed client outcomes.

#### Campaign plan: A campaign system before a content calendar
I connect the audience, offer, channel and follow up before deciding what to post or where to spend.
Problem: Activity is easy to measure. It is harder to tell whether the right people move from interest to a useful conversation.
Plan: Define one business objective and audience, shape the offer, map the landing experience and agree on the qualified outcome.
Decisions: Local service: specific problem, service area and a useful booking offer. Online store: a clear product use case, proof and transparent delivery terms. B2B service: a focused diagnostic for a named decision maker, not a broad pitch.
Testing before handoff: The ad promise must match the destination page. Source tags and conversion events must reach the CRM. Check qualification and lead ownership before increasing spend.
Handoff: Campaign brief, channel plan, landing page outline, content themes and measurement map.

#### Measurement: A measurement plan that follows the customer
The campaign click, captured enquiry and qualified outcome need to belong to the same measurement story.
Problem: A dashboard can show more leads while the sales team receives fewer useful opportunities.
Plan: Agree on event definitions, source naming and qualification rules. Check tracking quality before interpreting performance.
Decisions: Use consistent campaign source, medium and content tags. Keep a primary outcome and a small set of guardrail metrics. Review consent requirements and attribution limitations before adding tracking.
Testing before handoff: A form success event must not fire on a validation error. Repeated page loads must not become duplicate conversions. Compare platform reports with actual CRM outcomes.
Handoff: Event dictionary, UTM convention, tracking QA sheet and reporting structure.

#### Experiment plan: A test designed to teach us something
A useful test starts with a hypothesis and a decision rule, not two random ads and a quick winner.
Problem: Changing the audience, offer and creative together makes it difficult to understand what caused the result.
Plan: Choose one meaningful variable, define the control and variant, and agree on the primary metric and review window.
Decisions: Offer clarity: change the promise while keeping audience and destination stable. Creative angle: compare demonstration with the current creative using the same offer. Booking friction: reduce nonessential questions, then check lead quality as well as completion.
Testing before handoff: Confirm both variants receive comparable treatment. Look at downstream quality, not just click through rate. Do not declare a winner from inadequate or inconsistent evidence.
Handoff: Experiment brief, variant specification, measurement checklist and decision log.
